# Contributing to AutoFTE

Thanks for taking a look. This is a young project — the bar for small, focused PRs is low.

## Setup

```bash
git clone <your fork>
cd AutoFTE
python3 -m pip install -e ".[dev]"
```

## Before opening a PR

```bash
ruff check autofte tests scripts
pytest
```

Both need to pass — CI runs the same two checks. For a change that touches the
CLI, the demo path, or dashboard/report generation, also run
[`scripts/smoke-test.sh`](scripts/smoke-test.sh): it drives the real
`autofte` binary end to end (doctor, demo, triage, binscan, crash-info,
bench, pipeline, dashboard) rather than the mocked subprocess/filesystem
boundaries `pytest` uses, so it catches wiring breaks — a renamed flag, a
broken default path, a template that no longer renders — that the unit
suite can't see. It's not wired into CI (it builds real binaries and takes
longer than the unit suite), so it's on you to run it locally before a PR
that touches those layers.

## Commit style

This repo uses [Conventional Commits](https://www.conventionalcommits.org/):

- `feat:` a new capability (new subcommand, new check, new analysis backend)
- `fix:` a bug fix
- `docs:` README/CONTRIBUTING/docstrings only
- `chore:` packaging, CI, repo hygiene, dependency bumps
- `style:` formatting-only changes, no behavior change
- `refactor:` restructuring without changing behavior
- `test:` test-only changes

Keep commits scoped — one logical change per commit is easier to review and revert than one giant one.

## Adding a new check to `binscan`

Each protection check in `autofte/binary_analysis.py` is a small `_check_*` method on `BinaryAnalyzer` that shells out via the shared `_run_tool()` helper (handles missing tools/timeouts consistently) and returns a plain dict. Add a new method, wire it into `analyze_all_protections()`, and add a test in `tests/` that mocks `subprocess.run` with crafted tool output rather than depending on a real binary where possible.

## Recording the README demo assets

The README's hero embed is `autofte-demo-combined.gif`, a single stitched
recording: a terminal walkthrough of `autofte demo --verbose` followed by a
scroll through the dashboard it writes. It's the only demo asset actually
checked in. It's built from two intermediates — `autofte-demo.gif` (the
terminal recording alone) and `autofte-dashboard.png` (a full-resolution
screenshot of the static dashboard) — that exist only as local scratch
files during the steps below (both are gitignored; don't add them to a
PR). The combined GIF is regenerated by hand when the CLI output or
dashboard layout changes meaningfully — not on every commit.

**1. Terminal recording (`autofte-demo.gif`)**

Requires [asciinema](https://asciinema.org/) and
[agg](https://github.com/asciinema/agg) (the cast→GIF converter). If your
distro doesn't package `agg`, grab a prebuilt binary from its
[releases page](https://github.com/asciinema/agg/releases) — prefer the
`musl` build over the `gnu` one if you hit a `GLIBC_x.xx not found` error
running it.

You'll also need a working Ollama server with a model pulled. The demo has
been verified end-to-end with `glm-4.7-flash:latest`; `gpt-oss:20b` is known
to return empty responses against this pipeline and should not be used for
the recording.

```bash
asciinema rec --overwrite -c "bash scripts/record-demo.sh" \
  --idle-time-limit 2.5 autofte-demo.cast
agg --speed 1.3 --font-size 14 --theme monokai autofte-demo.cast autofte-demo.gif
```

`scripts/record-demo.sh` is the actual script asciinema runs — it's checked
in so the narration and pacing are reproducible rather than hand-typed live.
It runs `autofte demo --verbose` (not the bare default) specifically so the
recording shows real progress: the vulnerable source line under test, the
pre-generated crash count, the per-crash triage trace, and the final
verdict — not just a silent gap while the LLM call is in flight.
`--idle-time-limit 2.5` caps how long any single pause in the cast can be,
so LLM inference time doesn't turn into dead air in the GIF. Override the
model with `AUTOFTE_DEMO_MODEL=<name>` if you're recording against a
different one.

**2. Dashboard screenshot (`autofte-dashboard.png`)**

Requires [puppeteer](https://pptr.dev/) (`npm install puppeteer`), which
bundles its own headless Chromium — no system browser needed.

```bash
autofte demo --model glm-4.7-flash:latest   # writes autofte-demo-output/dashboard/
node scripts/screenshot-dashboard.mjs
```

This produces the same dashboard the terminal recording ends by writing, so
run it right after (or reuse the output from) the recording above rather
than a separate unrelated `autofte demo` run, to keep the two assets
telling the same story.

**3. Stitching them together (`autofte-demo-combined.gif`)**

Requires `ffmpeg` (and `ffprobe`, which ships with it) on `PATH`.

```bash
scripts/stitch-demo.sh   # reads autofte-demo.gif + autofte-dashboard.png,
                          # writes autofte-demo-combined.gif
```

`scripts/stitch-demo.sh` scales/crops both source assets onto a shared
canvas, turns the static dashboard PNG into a short clip that holds on the
top, middle, and bottom of the page, concatenates it after the terminal
clip, and re-encodes the result to GIF with ffmpeg's two-pass palette
technique. The hold-on-three-waypoints approach (rather than a smooth,
continuously-panning scroll) is deliberate: an earlier attempt at a
continuous pan produced a ~10MB GIF, because every frame of a continuous
pan is visually unique and compresses poorly. Holding on waypoints means
most consecutive frames are near-identical, which the encoder compresses
far better — the same content, under 1MB. Override the canvas size, frame
rate, or per-waypoint hold time with the `STITCH_WIDTH`, `STITCH_HEIGHT`,
`STITCH_FPS`, and `STITCH_HOLD_SECONDS` environment variables if you need
to retune it.

## Reporting bugs / proposing features

Open an issue. For anything nontrivial, a quick issue before a big PR saves everyone time.
